# アーキテクチャと技術選定

対象: MeetingRecorder（Windows 11 向けポータブル会議録音アプリ。文字起こしは録音後にローカルで実行）

---

## 0. 設計の最優先事項

要件で定められた優先順位をそのまま実装の制約にしています。

```
1. 録音の確実性
2. マイク音声・PC内部音声を正しく保持すること
3. 保存音声を文字起こしに適した状態で保持すること
4. 録音後の文字起こし精度
5. 操作の分かりやすさ
6. 議事録生成等の付加機能
```

**リアルタイム性はこの一覧に存在しません。** これは以前の版からの最大の変更で、
本ドキュメントのほぼすべての設計判断がここから導かれます。理由は一文です。

> 文字起こしは録音後に何度でも実行できる。しかし録音データを失えば復元できない。

この順位から導かれる不変条件（コード上の全設計判断の根拠）:

| 不変条件 | 実装上の担保 |
| --- | --- |
| 録音中に音声認識を実行しない | `RecordingPipeline` は `ISpeechRecognizer` を引数にも取らず、フィールドにも持たない。テスト `StartingARecordingNeverTouchesASpeechRecognizer` がリフレクションで両方を検査する |
| 録音開始のクリティカルパスにモデルロードを置かない | 認識器を生成する箇所はアプリ全体で `AppServices.TryCreateTranscriptionRecognizer` の1つだけで、呼び出し元は文字起こしコマンドのみ |
| 録音停止で文字起こしを始めない | `MeetingSessionManager.Stop` は会議フォルダーを完成させて戻るだけ。テスト `StoppingDoesNotStartATranscription` が保証 |
| 停止ボタンを押さなくてもデータが残る | WAV はヘッダ自己修復方式で逐次書き込み、認識結果は追記専用ジャーナルへ逐次追記 |
| 片方のデバイスが落ちても録音は続く | 各キャプチャは独立。失敗側は無音として合成され、警告を表示 |
| 発言元は推測しない | アプリ録音では系統別ファイルから、インポートでは「インポート音声」1種類。どちらもAI推測ではない |
| 音声に時間変動・非線形な加工をしない | ゲート／AGC／コンプ／リミッターは実装ごと削除。テスト `RemovedProcessingStagesTests` がアセンブリ内に型が存在しないことを検査 |
| 管理者権限を要求しない | WASAPI 共有モード、`SetThreadExecutionState`、ユーザー領域への書き込みのみ |

## 1. 技術選定

### 1.1 評価軸

要件どおり、以下を最重要評価基準としました。

```
Windows 11 / 管理者権限不要 / WASAPI Loopback / 長時間安定録音 /
ポータブル配布 / CPUローカルSTT（録音後） / GitHub Actions で再現可能なビルド /
保守性 / ライセンス
```

### 1.2 選定結果

| 領域 | 採用 | 主な理由 | 検討した代替案と不採用理由 |
| --- | --- | --- | --- |
| 言語 / ランタイム | C# / .NET 8 | WASAPI へ P/Invoke なしで到達でき（NAudio）、自己完結型 publish が標準機能、GitHub Actions の `windows-latest` に SDK が同梱 | C++/WinRT: 開発・保守コストが高い。Electron + Node: ランタイム同梱で 200MB 超、ネイティブ音声取得に追加バインディングが必要。Python: 配布に PyInstaller 等が必要で、要件の「Python 事前インストール禁止」を満たすのが難しい |

| 話者分離 | 自前実装（MFCC + オンラインクラスタリング） | 追加ダウンロードゼロ、CPU 負荷が小さく、実行タイミングを文字起こし時に移せる | pyannote / WeSpeaker 等のニューラル埋め込み: 数百MBの追加ダウンロードとライセンス確認が必要で、優先度9の機能としては過大 |

| テスト | xUnit | .NET 標準的、`dotnet test` で CI 統合が容易 | - |

  MeetingRecorder.Stt          net8.0        ← whisper.cpp アダプタ

  MeetingRecorder.App          net8.0-windows ← WPF

  MeetingRecorder.Stt.Tests    net8.0        ← モデルダウンロード整合性・認識器契約

**`Core` を `net8.0`（Windows 非依存）にしている理由**が設計上もっとも重要です。

というインターフェース越しに動くため、マイクもスピーカーも存在しない CI ランナー上で
「2ストリームを合成して1ファイルに書く」という中心的な振る舞いを丸ごとテストできます。

## 2. 音声パイプライン

### 2.1 スレッド構成

**録音中**（これがすべてです）:

```
[WASAPI capture callback]  ── mono float 変換 → レベルメーター → リングバッファ書き込み
   (OSスレッド, 最短経路)              │
                                       ▼
[pump スレッド AboveNormal] ── リング読み出し（不足分は無音補間）
                              → DCオフセット除去
                              → 16kHz へリサンプル → 系統別 WAV 書き込み
                              → 一定ゲインで加算 → ミックス WAV 書き込み
                                       │
                                       ▼
[UI スレッド]               ── 100ms ごとに状態をポーリング（Dispatcher 経由で反映）
```

pump の1ティックあたりの処理は、サンプルごとの数回の積和と2本のシーケンシャル書き込みだけです。
**推論もクラスタリングもアロケーションもこの経路にはありません。**
以前ここにあった VAD / チャンカー / STT キュー / STT ワーカーは、
すべて削除されました。

**文字起こし中**（ユーザーが押したときだけ・録音は行われていません）:

```
[スレッドプール]  ── モデルロード → WavFileReader で系統別ファイルを走査
                     → 無音位置で最大27秒に分割 → whisper.cpp 推論（beam 5）
                     → 話者クラスタリング → TranscriptStore へ
                             │
                             ▼
[UI スレッド]      ── Progress<T> 経由で進捗、完了時に本文を差し替え
```

AI 推論は UI スレッドでもキャプチャスレッドでも実行されません。
そして**キャプチャスレッドが存在する間は、どこでも実行されません。**

### 2.2 内部フォーマット

**48 kHz / モノラル / float32** を内部の正準フォーマットとしています。

- Windows 11 の WASAPI 共有モードは既定で 48 kHz。ここに合わせると再サンプルが 1 回で済みます。
- モノラル化はキャプチャコールバック内で実施（会議記録にステレオ定位は不要で、
  ファイルサイズと前処理コストが半分になります）。
- WAV 出力は 48 kHz / 16bit / モノラル = 96 kB/s ≒ **338 MB/時**。

### 2.3 マスタークロックと同期（要件24）

マイクと再生デバイスは別々の水晶発振器で駆動されるため、そのまま結合すると
1〜2時間で数百 ms のずれが蓄積します（民生機の典型値 50〜100 ppm ＝ 2時間で 0.36〜0.72 秒）。

対策:

1. **壁時計をマスターにする。** pump は `Stopwatch` の経過時間から
   「今までに何サンプル出力すべきか」を求め、その分だけ各ストリームから読み出します。
2. **不足分は無音を挿入する。** WASAPI ループバックは再生が完全に無音の間、
   パケットを一切返さないことがあります。この場合も出力タイムラインは壁時計どおりに進み、
   録音長と文字起こしのタイムスタンプが実時間とずれません。
3. **恒常的な余剰はごく少量ずつ捨てる。** `DriftCompensator` は
   平滑化したバックログが「目標100ms + 閾値150ms」を **5秒以上継続** した場合にのみ、
   1 tick あたり最大 1 ms 分を破棄します。無音後のバースト到着を
   ドリフトと誤認しないための時定数です（テスト `ABurstAfterSilenceIsNotMistakenForDrift`）。

補正上限は 1 tick(20ms) あたり 1 ms ＝ 最大 5% のクロック誤差まで吸収でき、
実機の誤差（0.01% 程度）に対して 2 桁以上の余裕があります。

### 2.4 音声処理の方針

**このアプリが音声に対して行う処理は、以下がすべてです。**

| 対象 | 処理 |
| --- | --- |
| 認識用音声（`recognition-*.wav`） | DCオフセット除去 → 16kHz へリサンプル → モノラル → 16bit PCM |
| 保存音声（`meeting.wav`） | DCオフセット除去 → 各系統に一定 -6.02 dB → 加算 → **録音終了後にファイル全体へ一定ゲイン1回** |

以前の版にあった **ソフトノイズゲート / ラウドネス正規化(AGC) / コンプレッサー /
リミッターは、無効化ではなく実装ごと削除**しました。

**なぜ削除したか。** これらはいずれも「ゲインを時間の関数として変える」処理です。
一方 Whisper が特徴量として読んでいるのは、まさにその**振幅包絡の形**です。
つまり人間の耳のための加工が、そのまま認識器への入力を歪めます。影響は
**小さな声ほど大きく**なり、本製品が対象とする会話音声で最も損なわれます。

保存音声にも適用しない理由は、この録音の主用途が「あとから文字起こしすること」
だからです。音楽的・放送的に聞きやすい音声を作ることは目的ではありません。

削除されたことは `RemovedProcessingStagesTests` がアセンブリ内の型名と
`AudioProcessingSettings` のプロパティ名の両方で検査しています。
「設定で無効化されている」ではなく「存在しない」ことを検査するのは、
無効化された段は設定ひとつで復活してしまうためです。

### 2.5 音量調整（単一固定ゲイン）

```
peak = max |input[n]|                          （ファイル全体を走査）
gain = min( 10^(target/20) / peak , 10^(max/20) )
output[n] = input[n] * gain                    （全サンプルに同じ gain）
```

`gain` は `n` に依存しません。したがって**線形かつ時不変**であり、話し始めの小さい音・
子音・小声・大声・無音・発話のダイナミクスの相対関係は一切変化しません。
テスト `EveryNonZeroSampleIsMultipliedByTheSameConstant` が、
非ゼロサンプルに対する `output[n] / input[n]` が許容誤差内で一定であることを検査します。

| 定数（`AudioProcessingSettings`） | 値 | 根拠 |
| --- | --- | --- |
| `DcBlockerCutoffHz` | 20 Hz | 成人男性の最低基本周波数（約80 Hz）の1オクターブ下。DCオフセットはヘッドルームを消費して後段の固定ゲインを小さくし、ピーク測定も歪めるため残している |
| `MixGainPerStreamDb` | **-6.0206 dB（= ちょうど 0.5 倍）** | 2系統が同時にフルスケールでも合計がちょうどフルスケールに収まる唯一の値。リミッターもクランプも使わずにクリップを算術的に不可能にする。失った 6 dB は録音終了後の固定ゲインで返す |
| `NormalizationTargetPeakDbFs` | **-1.0 dBFS** | PCM のサンプルピークは、DA変換や非可逆圧縮でサンプル間に再構成される真のピークと一致しない。ITU-R BS.1770-4 / EBU R 128 が同じ理由で -1 dBTP の余裕を推奨しており、同じ値を同じ理由で採る。16bit 量子化の丸めもここに吸収される |
| `MaxNormalizationGainDb` | **+20.0 dB（= 10倍）** | これ以上増幅しても持ち上がるのは発話ではなく収録時のノイズフロア。ノイズを10倍より大きくしても会議は聞き取りやすくならない。ゲインを一定に保ったまま「大きくしすぎない」という制限であり、リミッターではない |
| `NormalizationSkipThresholdDb` | 0.1 dB | 約1.2%。可聴でなく、16bit へ再量子化する価値もない差。この場合はファイルを書き直さないため、pump が書いたバイト列がそのまま残る |
| `ClipDetectionThreshold` / `ClipDetectionSampleFraction` | 0.999 / 0.0001 | 1時間の録音で数サンプルがフルスケールに触れるのは偶然であって歪みではない。1万分の1（サンプルレートによらず、1時間あたり 3600 × 0.0001 = 約0.36秒分のサンプル）は、狼少年にならず、かつ実際に過大入力された録音は捕捉できる境界 |

**クリッピングはゲインを先に決めることで防ぎます。** サンプルループの中に閾値判定は
存在せず、大きすぎた値を潰す段もありません（`AHotFileIsScaledDownRatherThanHavingItsPeaksFlattened`）。
`WavFileWriter` に残るクランプは NaN や異常値に対する算術的な最後の砦であり、
クリッピング対策ではありません。

**書き直しの安全性。** 正規化は隣に一時ファイルを書いてから置換します。
途中でクラッシュしても、ディスクが埋まっても、pump が書いた録音がそのまま残ります。
音量調整を失うのは残念ですが、会議を失うのは許容できません。

**元音声が既にクリップしている場合**は、ログ・警告・`metadata.json` の
`sourceClipped` に記録します。**「修復できた」とは表示しません。**
潰れたピークは後処理では復元できないためです。

### 2.6 バックプレッシャーは存在しません

以前は録音と同時に認識を行っていたため、認識が遅れたときに音声をどう保持するかという
問題（`SttScheduler` のディスク退避）がありました。**録音中に認識を行わないため、
この問題そのものが存在しません。** `SttScheduler` と `.stt-spill/` は削除されました。

## 3. 音声認識（録音後のみ）

### 3.1 いつ動くか

**ユーザーが「文字起こし」を押したときだけ**動きます。それ以外に起動する経路は
ありません。認識器を生成するコードはアプリ全体で `AppServices.TryCreateTranscriptionRecognizer`
の1箇所で、その呼び出し元は `MainViewModel.TranscribeAsync` だけです。

- 録音開始時にモデルを読み込みません（読み込む理由がありません）。
- 録音中に推論しません。
- 録音停止で自動的に開始しません（`Stop` は会議フォルダーを完成させて戻ります）。
- 二重実行は、コマンドの実行可否と `WorkflowState` の両方で防いでいます。

対象は `OfflineTranscriptionService` に渡される 16 kHz の作業音声で、
アプリ録音なら系統別2本、インポートなら1本です。

### 3.2 発言元は録音の事実（アプリ録音の場合）

要件は「発言元は AI 推測ではなく録音元ストリームで決定する」ことを求めています。
そのため、認識が読むのは**混合ファイルではなく系統別の音声**です。混ぜてしまうと
発言元は推測に退化し、しかも**二度と復元できません**。系統別ファイルは録音中にしか
作れないため、録音中に 16 kHz で書き出しています（1系統あたり毎時約115MB）。

窓は `SpeechChunker` が無音位置で切り、生成時に発生元ストリームが刻印されます。
「マイク」「PC音声」は最後まで録音の事実であって、モデルの出力ではありません。

**インポート音声では音源が1本しかありません。** どちらがマイクでどちらが
PC音声かも、誰が話しているかも、その1本には記録されていません。したがって
`AudioSourceKind.Imported`（表示名「インポート音声」）を付けるだけで、
分類も話者クラスタリングも行いません。UI の「話者名を編集」も無効になり、
押した場合は理由を表示します。

### 3.3 認識に渡す音声は加工しない

**初期実装の誤りとその修正（経緯）。** 当初、認識器には録音ファイルと同じ音声、
つまりノイズゲート → ラウドネス正規化 → コンプレッサー → リミッターを通過した後の
音声を渡していました。実使用で「はっきり発音しないと認識されない」という報告があり、
原因はここでした。次にこれを分岐させ、認識側だけ DC 除去のみにしました。

**現在は、その分岐自体が不要になりました。** ゲート・正規化・コンプ・リミッターは
削除されたため、分岐すべき差がありません（2.4 節）。

```
キャプチャ → ミュート判定 → DC除去 ─┬─→ 16kHz リサンプル → 認識用 WAV（系統別）
                                      │
                                      └─→ 一定 -6.02 dB で加算 → 録音ファイル
                                              → 停止後にファイル全体へ一定ゲイン1回
```

`TheWorkingAudioIsTheCapturedAudioRatherThanAProcessedVersionOfIt` が、既知の
レベルのトーンを流し込んで、認識用ファイル側がそのレベルのまま届くことを検査します。

### 3.4 窓の切り方

| 設定 | 値 | 理由 |
| --- | --- | --- |
| 最大窓長 | **27 秒** | Whisper の受容野は 30 秒。これを超える窓はエンジン側で黙って切り捨てられるため、**切る位置をこちらで決め、必ず無音に置く** |
| 無音フラッシュ | **800 ms** | これより短い無音では窓を閉じない。文中の間で切らず、本当の区切りだけで閉じるため |
| オーバーラップ | 200 ms | 無音ではなく長さで切らざるを得なかった窓の継ぎ目で、単語が両断されないように |
| プリロール | 300 ms | 語頭の子音を欠かないように |

短い数秒のチャンクを毎回文脈なしで処理する方式（旧・速報パス）は使いません。
**録音に追いつく必要がなくなったため、精度側に振れるようになった**というのが唯一の理由です。

### 3.5 話者分離の実行タイミング

話者クラスタリングは `OfflineTranscriptionService` の内部で、認識器の直後、
**同じスレッド**で実行されます。録音中には実行しません。
「あとからでもできる処理を、取り返しのつかないものが動いている最中に走らせない」
という原則をそのまま適用しています。

失敗しても「話者不明」に縮退するだけで、誤った話者を付けることも、
文字起こしを中断することもありません。

### 3.6 whisper.cpp の設定

| 設定 | 値 | 理由 |
| --- | --- | --- |
| `WithNoContext()` | 有効 | 1つのエンジンにマイク／PC音声の窓が交互に入るため、デコーダの文脈を持ち越すと「部屋の発言に条件付けされた、流暢だが誤った remote 側の文」が生成される。会議記録では最悪の故障モード。窓**内部**の文脈は失われず、窓は無音位置で受容野いっぱいまで取るため、文が必要とする文脈は失っていない |
| サンプリング | **beam 5** | ビームサーチは greedy の約2倍のコスト。誰も待っていないため、最も安価な精度改善として採用。5 は whisper 自身の参照値 |
| `WithPrompt()` | 日本語の短い定型文 | プロンプトなしでは日本語が**句読点なしの一続き**で返ることが多く、会議記録として読み返しにくい。内容ではなく文体の指定であり、出力には現れない |
| `WithTemperatureInc()` | **0.2** | 温度フォールバックは崩れたデコードを再試行して救う。時間がかかるのは救う必要があった箇所だけで、待っているものは何もない |
| `NoSpeechProbability > 0.85` を破棄 | 有効 | Whisper は無音に対し「ご視聴ありがとうございました」等の定型句を出すことがある。文字列のブラックリストではなく **モデル自身が出す指標** で落とすため、正規の発話を誤削除しにくい |
| 最短入力 1 秒 | 無音パディング | whisper.cpp が 1 秒未満を扱えないため。短い返事を捨てずに認識させる |

### 3.7 モデル選定と性能自動調整

ユーザーは「高速／標準／高精度」を選びません。既定値はこの端末の実測から決まり、
**設定画面でいつでも上書きできます**。

1. `CapabilityProbe` が **実測**します（CPU 型番は使いません）。
   96×96 の密行列積を 1 スレッド／推奨スレッド数で実行し、
   ウォームアップ後のスループットを i5-1335U の P コア相当 = 1.0 として正規化。
2. `ProfileSelector` が **梯子の上から降りてきます**。以前は下から登っていました。
   録音に追いつく必要がなくなったため、判断基準が
   「間に合うか」から「**このPCが保持できて、待てる時間で終わる中で最も精度が高いのはどれか**」
   に変わったためです。
3. 自動選択の上限は `AcceptableProcessingFactor = 1.5`（1時間の録音に約1時間半）。
   これを超えるモデルは**自動では選ばれません**が、設定画面には常に全モデルが並び、
   選べば推定処理時間が表示されます。
4. RAM が「モデル所要量 × 3」に満たない場合は選びません（Windows・ブラウザ・
   会議クライアントと共存させるため）。

**実行時の機能縮退（degradation ladder）は削除しました。** あれは「リアルタイムに
追いつけないときに何を諦めるか」という仕組みであり、追いつく相手が存在しません。
処理が長いことは障害ではなく、ユーザーが選んだ待ち時間です。

### 3.8 モデル候補

| id | ファイル | サイズ（実測バイト） | 用途 |
| --- | --- | --- | --- |
| `whisper-tiny-q5_1` | `ggml-tiny-q5_1.bin` | 32,152,673 | 最軽量 |
| `whisper-base-q5_1` | `ggml-base-q5_1.bin` | 59,707,625 | 軽量 |
| `whisper-small-q5_1` | `ggml-small-q5_1.bin` | 190,085,487 | バランス |
| `whisper-medium-q5_0` | `ggml-medium-q5_0.bin` | 539,212,467 | 高精度 |
| `whisper-large-v3-turbo-q5_0` | `ggml-large-v3-turbo-q5_0.bin` | **574,041,195** | 最高精度 |

サイズと SHA-256 は `.github/workflows/model-hashes.yml` が配布元から実際に
ダウンロードして測定した値です。**推測した値は1つもありません。**

**large-v3-turbo を追加した理由。** large-v3 のエンコーダー（32層 / d=1280）を
そのまま持ち、デコーダーが4層に蒸留されているモデルです。whisper.cpp の CPU 実行では
エンコーダーが支配的なので「large 級のエンコーダーを、この階級のマシンで人が待てる
時間内に回す」唯一の現実的な選択肢になります。リアルタイム制約があったときには
検討する意味すらありませんでした。

**互換性の確認方法。** Whisper.net 1.8.1 が同梱する whisper.cpp が turbo 形式に
対応していることは、`.github/workflows/build-windows.yml` の `evaluate_models`
入力で実際にモデルをダウンロードし、製品と同じデコード設定で推論させて確認しています。
依存パッケージのバージョンは変更していません。

**採用しなかった量子化。** 同時に測定した q8_0（874,188,075 バイト）と
f16（1,624,555,275 バイト）はカタログに載せていません。16GB の環境で Windows・
ブラウザ・会議クライアントと共存させる余裕が乏しく、`RequiredRamMb × 3` の
条件を満たさないためです。

**未実測であること。** 基準PC（Core i5-1335U / RAM 16GB）での実処理時間と
メモリ使用量は測定していません。`RelativeCost` はエンコーダーの計算量
（層数 × 次元²）から導いた**推定値**です。

```
small        12 層 × 768²  =  7.08M  → 1.0（基準）
medium       24 層 × 1024² = 25.17M  → 3.6
large-v3-turbo 32 層 × 1280² = 52.43M → 7.4
```

デコーダーを意図的に無視しているため、**large-v3-turbo にとっては悲観的**な値です
（turbo はデコーダーが 4 層しかありません）。補正するにはその会議のトークン数と
フレーム数の比を仮定する必要があり、そちらのほうが根拠が弱くなります。
悲観側に外すほうが安全でもあります — 自動選択が保守的になるだけで、
ユーザーが想定より長く待たされることはありません。

この値が影響するのは**既定のモデル選択と、設定画面に表示する目安**だけです。
どのモデルも手動で選べますし、UI 上も「実測値ではなく推定です」と明示しています。

### 3.9 GPU

**GPU は必須にしていません。CPU が唯一の必須経路です。**
Whisper.net は OpenVINO エンコーダを指定できますが、
Intel 内蔵GPU での安定性・ドライバ依存・配布サイズ増を勘案し、
既定では有効化していません。将来的に有効化する場合も CPU フォールバックは維持します。

## 4. 話者分離（実験的）

**実行タイミング: 文字起こし中のみ。録音中には実行しません。**

- 各発話区間から **MFCC 1〜12 の平均と標準偏差（24次元）** を作り、L2 正規化。
- 既存クラスタとのコサイン類似度が **0.82** 以上なら同一話者、なければ新規クラスタ。
- クラスタはキャプチャストリームごとに独立（マイク側と PC 音声側で番号を共有しない）。
- クラスタ上限 8。

**限界を明記します。** これはニューラル話者埋め込みではありません。
重なった発話は分離できず、声質の似た2人は統合され、
マイクとの距離が変わった同一人物は分割されることがあります。
そのため:

- 発言元の「マイク / PC音声」は **常に**録音元ストリームで決定され、話者分離の成否に依存しません。
- 人物名を AI が推測することはありません。`Speaker 1`, `Speaker 2` のみを付与し、
  実名はユーザーが入力した場合のみ表示されます（会議内の同一話者へ一括反映）。
- **インポートした音声には適用しません。** 1本の音声には音源の情報がないため、
  クラスタリングした結果に意味づけできる根拠がありません。UI 側でも
  「話者名を編集」を無効化し、理由を表示します。
- この限界は README.md の「既知の制約」にも同じ表現で記載しています。

## 5. 議事録生成（実験的・要件44-47）

2つの生成器があります。

| 生成器 | 依存 | 動作 |
| --- | --- | --- |
| `ExtractiveMinutesGenerator` | なし（常に利用可能） | 決定・アクション・継続検討のキューフレーズに一致する文を **原文のまま**タイムスタンプ付きで抽出。10分ブロックごとに議題を整理 |
| `LocalLlmMinutesGenerator` | llama.cpp + GGUF | ブロック要約（map）→ 4 セクション生成（reduce）の 2 段構成。失敗時は抽出型へフォールバック |

共通の方針:

- **文字起こし結果が存在する場合にのみ、ユーザーがボタンを押したときだけ実行**します。
  録音しただけの状態ではコマンドが無効です。議事録は文字起こしの本文から作るもので、
  本文がなければ作れるものが何もないためです。
- 出力の骨格は `MinutesTemplate` が組み立てるため、モデルが脱線しても6セクションは必ず存在します。
- プロンプトは「文字起こしにない情報を書かない」「担当者・期限が明記されていなければ
  必ず `要確認`」「人物名を推測しない」を明示。
- 進捗は実際に処理したブロック数（偽の進捗バーではありません）。

## 6. 永続化とクラッシュ復旧（要件50-51）

アプリで録音した会議:

```
2026-09-07_1430_Meeting/
├── meeting.wav              逐次書き込み（ヘッダを毎フラッシュで更新）
│                            停止後に一定ゲインを1回適用（一時ファイル経由で置換）
├── recognition-mic.wav      16kHz 系統別。文字起こしの入力
├── recognition-system.wav   同上
├── transcript.txt / .md     停止時・文字起こし完了時・編集時に生成
├── minutes.txt / .md        「議事録を生成」実行時
├── metadata.json            原子的書き込み（.tmp → Replace）
└── session.journal          録音中のみ存在。追記専用 JSON Lines
```

インポートした音声:

```
2026-09-07_1512_interview/
├── recognition-import.wav   元ファイルから復号した 16kHz 作業音声
├── transcript.txt / .md
├── minutes.txt / .md
└── metadata.json            isImported / importedFromPath を含む
```

**インポート元のファイルはコピーしません。** 会議フォルダーに入るのは作業音声だけで、
音声の本体はユーザーが置いた場所に残ります。`metadata.json` にパスを記録しているため、
作業音声を削除したあとでも、元ファイルが同じ場所にあれば作り直して再文字起こしできます。

ファイル名は従来の仕様と後方互換です。`.stt-spill/` は
（それを必要としていた仕組みごと）廃止されました。

- **WAV ヘッダ自己修復**: フラッシュのたびに RIFF/data サイズを実書き込み量で書き直します。
  プロセスが強制終了しても、残ったファイルはそのまま再生できます（修復ツール不要）。
- **追記専用ジャーナル**: 認識結果・編集・進捗を1行1JSONで追記。
  電源断で最終行が途中で切れても、その行を読み飛ばすだけで直前までが完全に復元されます
  （テスト `JournalReplayReconstructsEverySegmentEvenAfterATornLastLine`）。
- **起動時スキャン**: 保存先に「完了していないジャーナル」を持つフォルダがあれば
  復旧ダイアログを表示します。「復旧しない」を選んでも音声ファイルは削除しません。
- **作業音声の削除条件**: `RecognitionAudioCleanup` が唯一の判断箇所で、
  規則は「ユーザーが削除を選んでいて、**かつ**文字起こしが正常完了した場合のみ」です。
  失敗・中止では削除しません。次にやることは「もう一度試す」であり、入力を消すと
  それができなくなるためです。アプリ録音の系統別音声は**どこからも復元できません**。

## 7. デバイス変更とスリープ（要件52-53）

- キャプチャが予期せず停止した場合、最大 5 回・線形バックオフ（0.5s, 1.0s, ...）で
  デバイスを再解決して再接続します。成功／失敗のいずれも `CaptureFault` として
  UI に日本語で通知します。**自動復帰できない場合は明示します**（要件52）。
- スリープ抑制は `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` を
  **専用スレッド**から呼びます。スレッドプールから呼ぶとスレッド回収時に要求が失われます。
  `ES_DISPLAY_REQUIRED` は要求しません（画面ロックポリシーを上書きしない）。
  プロセス終了時に自動解除されるため、クラッシュしても設定は残りません。管理者権限は不要です。

## 9. 配布とビルド

- `dotnet publish -r win-x64 --self-contained true` による自己完結型配布。
  .NET / VC++ / Python / Node.js の事前インストールは不要です。
- **トリミングは無効**: WPF はトリム非対応であり、Whisper.net と LLamaSharp は
  ネイティブアセットと型をリフレクションで解決します。ZIP がやや大きくなる代わりに
  「展開したら動く」ことを優先しました。
- **単一 EXE にはしていません**: 要件でも必須とされておらず、
  単一ファイル化はネイティブライブラリの展開を伴い起動が遅くなるためです。
- **llama.cpp の命令セット別レイアウトを保持しています**: LLamaSharp は
  `noavx / avx / avx2 / avx512` の 4 種のネイティブバイナリを同梱し、
  実行時に上から順にロードを試みます。RID 指定の publish は既定で
  `runtimes/<rid>/native/` を出力ルートへ平坦化するため、
  4 種が同名で衝突して `NETSDK1152` になります。
  仮に平坦化に成功しても危険です — 1 種類しか同梱されず、
  AVX-512 非対応の PC で AVX-512 ビルドを読み込むと
  「不正な命令」で即座に落ちます。そのため publish ターゲットで
  元のパッケージ内パスへ戻し、CI で 4 種の存在とルートに
  `llama.dll` が無いことを検証しています。
- CI は `windows-latest` 上で restore → build → test → publish → ZIP → artifact を実行し、
  publish 出力に `MeetingRecorder.exe` / ランタイム / whisper ネイティブが存在すること、
  および **AIモデルが混入していないこと** を検証します。
- `build-windows.yml` の手動実行では `evaluate_models` 入力に ggml ファイル名を渡せます。
  指定したモデルを実際にダウンロードし、製品と同じデコード設定で推論させ、
  サイズ・SHA-256・読み込み時間・ワーキングセット・処理時間を出力します。
  **カタログにモデルを追加する前に、実際に動くことを確かめるための入口です。**
  空（既定）のときは通常のビルドと変わりません。
- **WPF を含む完全なビルドは Windows でしか行えません。** Linux では
  `Core` / `Stt` / `Diarization` / `Minutes` / `Audio` とそのテストのみビルド・実行できます
  （`.NET SDK` の WindowsDesktop コンポーネントが非 Windows 版に含まれないため）。
  したがってアプリ本体のコンパイル確認は CI が唯一の手段です。

## 10. CI で検証できないこと

`docs/WINDOWS_E2E_TEST.md` と `TEST_RESULTS.md` に一覧があります。要点のみ:

GitHub-hosted の Windows ランナーには実マイク・実スピーカー・実オーディオセッションが
ありません。したがって **CI のビルド成功は WASAPI 実機動作の確認を意味しません。**
実機確認が必要な項目（マイク録音、ループバック取得、Zoom/Meet/Teams 実音声、
長時間録音、CPU/RAM 実測、SmartScreen、i5-1335U での文字起こし実性能）は
すべて「Windows 実機確認が必要」として分類しています。

この改修で追加された未検証項目:

| 項目 | 状態 |
| --- | --- |
| 基準PC（i5-1335U）での medium / large-v3-turbo の実処理時間・RAM | **未実測**。設定画面の表示は推定値であることを明示 |
| 生の ADTS `.aac` ファイルのインポート | **未検証**。CI で真の ADTS を生成する手段がないため。MP4 コンテナの AAC（`.m4a`）は往復テスト済み |
| Windows N / KN での MP3 / M4A / AAC インポート | **未検証**（Media Feature Pack 非導入環境が CI にない）。WAV は OS コーデックに依存しないため影響を受けません |
| 日本語会議音声での実認識精度 | **未測定**。CI の合成音声は英語（Windows ランナーに日本語音声がないため） |
