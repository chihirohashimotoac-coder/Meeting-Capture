# アーキテクチャと技術選定

対象: MeetingRecorder（Windows 11 向けポータブル会議録音・リアルタイム文字起こしアプリ）

---

## 0. 設計の最優先事項

要件で定められた優先順位をそのまま実装の制約にしています。

```
1. 録音データを失わない
2. PCマイクを録音できる
3. PC内部音声を録音できる
4. 両方を長時間同期できる
5. 音量差を補正できる
6. WAV / MP3 で保存できる
7. 日本語文字起こし
8. 操作性
9. Speaker diarization
10. Local LLM 議事録
```

この順位から導かれる不変条件（コード上の全設計判断の根拠）:

| 不変条件 | 実装上の担保 |
| --- | --- |
| STT が遅れても録音は絶対に巻き込まない | STT は専用スレッド（`BelowNormal`）＋キュー越し。例外は捕捉してログのみ。`RecordingPipeline` の pump スレッドは STT の状態を一切参照しない |
| 音声データを捨てて追いつかせない | `SttScheduler` はキューが閾値を超えるとメモリではなくディスクへ退避（spill）する。ドロップは実装上存在しない |
| 停止ボタンを押さなくてもデータが残る | WAV はヘッダ自己修復方式で逐次書き込み、認識結果は追記専用ジャーナルへ逐次追記 |
| 片方のデバイスが落ちても録音は続く | 各キャプチャは独立。失敗側は無音として合成され、警告を表示 |
| 管理者権限を要求しない | WASAPI 共有モード、`SetThreadExecutionState`、ユーザー領域への書き込みのみ |

## 1. 技術選定

### 1.1 評価軸

要件どおり、以下を最重要評価基準としました。

```
Windows 11 / 管理者権限不要 / WASAPI Loopback / 長時間安定録音 /
ポータブル配布 / CPUローカルSTT / GitHub Actions で再現可能なビルド /
保守性 / ライセンス
```

### 1.2 選定結果

| 領域 | 採用 | 主な理由 | 検討した代替案と不採用理由 |
| --- | --- | --- | --- |
| 言語 / ランタイム | C# / .NET 8 | WASAPI へ P/Invoke なしで到達でき（NAudio）、自己完結型 publish が標準機能、GitHub Actions の `windows-latest` に SDK が同梱 | C++/WinRT: 開発・保守コストが高い。Electron + Node: ランタイム同梱で 200MB 超、ネイティブ音声取得に追加バインディングが必要。Python: 配布に PyInstaller 等が必要で、要件の「Python 事前インストール禁止」を満たすのが難しい |
| UI | WPF | .NET 8 に同梱、単一 EXE 不要のポータブル配布と相性が良い、日本語 IME と高DPIに実績 | WinUI 3: Windows App SDK の再配布が必要でポータブル配布が複雑になる。WinForms: レベルメーター等の描画が古く保守性が低い |
| 音声取得 | WASAPI（NAudio 2.2.1 経由） | 共有モードのループバックは追加ドライバ・管理者権限なしで「再生デバイスの出力全体」を取得できる唯一の実用手段 | Stereo Mix: 搭載はサウンドカード依存で現代のノートPCにはほぼ無い。VB-CABLE 等の仮想デバイス: インストーラーと管理者権限が必要（要件で禁止）。プロセス単位ループバック (ActivateAudioInterfaceAsync + PROCESS_LOOPBACK): 特定アプリ専用になり「PC再生音全体」という要件に反する |
| 音声認識 | whisper.cpp（Whisper.net 1.8.1） | CPU のみで動作、量子化モデルでメモリ帯域律速の省電力CPUに適合、ggml モデルは MIT、ネイティブバイナリが NuGet で配布されビルドが再現可能、日本語性能が実用水準 | Vosk: 日本語モデルの精度が Whisper small に届かない。Azure/Google/AWS STT: クラウド送信となり要件違反。ONNX Runtime + Whisper ONNX: 変換済みモデルの配布・ライセンスが不透明でビルド再現性が低い |
| MP3 エンコード | Windows Media Foundation（NAudio 経由） | OS 同梱のためバイナリ追加ゼロ、LGPL 義務が発生しない | LAME / NAudio.Lame: LGPL のネイティブ DLL 同梱が必要。要件を満たせないわけではないが、社内配布のライセンス確認コストを避けた |
| 話者分離 | 自前実装（MFCC + オンラインクラスタリング） | 追加ダウンロードゼロ、CPU 負荷が小さく、要件の「重ければ2分類にフォールバック」と整合 | pyannote / WeSpeaker 等のニューラル埋め込み: 数百MBの追加ダウンロードとライセンス確認が必要で、優先度9の機能としては過大 |
| ローカルLLM | llama.cpp（LLamaSharp 0.24.0）+ Qwen2.5-1.5B-Instruct GGUF | CPU 推論、Apache-2.0 で社内商用利用の可否が明確、日本語性能がサイズ比で良好、GGUF 公式配布あり | Llama 3.2: ライセンスが Llama Community License で商用条件の確認が必要。Qwen2.5-3B 以上: 研究用ライセンスまたは基準PCで実用速度に届かない |
| テスト | xUnit | .NET 標準的、`dotnet test` で CI 統合が容易 | - |

### 1.3 プロジェクト構成

```
src/
  MeetingRecorder.Core         net8.0        ← プラットフォーム非依存。DSP・パイプライン・永続化・STT抽象
  MeetingRecorder.Audio        net8.0-windows ← WASAPI / Media Foundation / スリープ抑制
  MeetingRecorder.Stt          net8.0        ← whisper.cpp アダプタ
  MeetingRecorder.Diarization  net8.0        ← MFCC + クラスタリング
  MeetingRecorder.Minutes      net8.0        ← 抽出型 + ローカルLLM議事録
  MeetingRecorder.App          net8.0-windows ← WPF
tests/
  MeetingRecorder.Core.Tests   net8.0        ← DSP/パイプライン/永続化/話者分離/議事録
  MeetingRecorder.Stt.Tests    net8.0        ← モデルダウンロード整合性・認識器契約
  MeetingRecorder.Audio.Tests  net8.0-windows ← WASAPI 層（実機依存部分は明示的に対象外）
  MeetingRecorder.App.Tests    net8.0-windows ← WPF 画面ロード・データバインド検証
```

**`Core` を `net8.0`（Windows 非依存）にしている理由**が設計上もっとも重要です。
録音パイプライン全体が `IAudioCaptureSource` / `IAudioFileWriter` / `ISpeechRecognizer`
というインターフェース越しに動くため、マイクもスピーカーも存在しない CI ランナー上で
「2ストリームを合成して1ファイルに書く」という中心的な振る舞いを丸ごとテストできます。

## 2. 音声パイプライン

### 2.1 スレッド構成

```
[WASAPI capture callback]  ── mono float 変換 → レベルメーター → リングバッファ書き込み
   (OSスレッド, 最短経路)              │
                                       ▼
[pump スレッド AboveNormal] ── リング読み出し（不足分は無音補間）
                              → per-stream DSP → ミックス → WAV 書き込み
                              → 16kHz へリサンプル → VAD → チャンク化 → STT キュー投入
                                       │
                                       ▼
[STT ワーカー BelowNormal]  ── whisper.cpp 推論 → 話者分離 → TranscriptStore へ
                                       │
                                       ▼
[UI スレッド]               ── 100ms ごとに状態をポーリング（Dispatcher 経由で反映）
```

AI 推論は UI スレッドでもキャプチャスレッドでも実行されません。

### 2.2 内部フォーマット

**48 kHz / モノラル / float32** を内部の正準フォーマットとしています。

- Windows 11 の WASAPI 共有モードは既定で 48 kHz。ここに合わせると再サンプルが 1 回で済みます。
- モノラル化はキャプチャコールバック内で実施（会議記録にステレオ定位は不要で、
  ファイルサイズと STT 前処理コストが半分になります）。
- WAV 出力は 48 kHz / 16bit / モノラル = 96 kB/s ≒ **338 MB/時**。

### 2.3 マスタークロックと同期（要件24）

マイクと再生デバイスは別々の水晶発振器で駆動されるため、そのまま結合すると
1〜2時間で数百 ms のずれが蓄積します（民生機の典型値 50〜100 ppm ＝ 2時間で 0.36〜0.72 秒）。

対策:

1. **壁時計をマスターにする。** pump は `Stopwatch` の経過時間から
   「今までに何サンプル出力すべきか」を求め、その分だけ各ストリームから読み出します。
2. **不足分は無音を挿入する。** WASAPI ループバックは再生が完全に無音の間、
   パケットを一切返さないことがあります。この場合も出力タイムラインは壁時計どおりに進み、
   録音長と文字起こしのタイムスタンプが実時間とずれません。
3. **恒常的な余剰はごく少量ずつ捨てる。** `DriftCompensator` は
   平滑化したバックログが「目標100ms + 閾値150ms」を **5秒以上継続** した場合にのみ、
   1 tick あたり最大 1 ms 分を破棄します。無音後のバースト到着を
   ドリフトと誤認しないための時定数です（テスト `ABurstAfterSilenceIsNotMistakenForDrift`）。

補正上限は 1 tick(20ms) あたり 1 ms ＝ 最大 5% のクロック誤差まで吸収でき、
実機の誤差（0.01% 程度）に対して 2 桁以上の余裕があります。

### 2.4 音量補正チェーン（要件22・23）

各ストリームに **独立して** 以下を適用してから合成します。

```
DC ブロッカー → ソフトノイズゲート → ラウドネス正規化(AGC) → コンプレッサー → リミッター
```

| 段 | 既定値 | 根拠 |
| --- | --- | --- |
| DC ブロッカー | 20 Hz ハイパス | 一部の USB マイク／仮想エンドポイントの DC オフセットがヘッドルームを食い、AGC の RMS 測定を歪めるため |
| ノイズゲート | しきい値 -52 dBFS、**最大減衰 12 dB**、ホールド 300 ms | 完全ミュートは「はい」「うん」等の相槌や語尾を消す。要件が明示的に禁止しているため、減衰量を制限した downward expander とした |
| AGC | 目標 **-20 dBFS RMS**、ゲイン範囲 **-12〜+18 dB**、追従 **1.5 dB/s**、無音時は凍結 | -20 dBFS は放送のラウドネス実務と同オーダーで、クレストファクタ用に約 20 dB のヘッドルームが残る。+18 dB 上限は、-60 dBFS のノイズフロアを可聴域まで持ち上げずに小声を回復できる境界。1.5 dB/s の緩慢な追従は「pumping」（文の切れ目でノイズが持ち上がる現象）を防ぐ。無音時凍結がないと、間の空いた瞬間にゲインが上がり次の発話で急降下する |
| コンプレッサー | -18 dBFS / 2.5:1 / ソフトニー 6 dB / attack 10ms / release 200ms | 強い圧縮は語間のノイズフロアを持ち上げ、Whisper が無音に対して定型句を出力する傾向を強める。マイクに近い話者と部屋の奥の話者の差を詰める最小限にとどめた |
| リミッター | 天井 **-1 dBFS**、先読み 5 ms、release 50ms、**最終ハードクランプ付き** | 16bit 量子化時のラップアラウンド（クリック雑音）を数学的に排除するため、エンベロープ追従に加えて最終段で必ずクランプする。テスト `NeverExceedsTheCeilingEvenForGrosslyHotInput` が保証 |
| ミキサー | 合計後 **-3 dB** のヘッドルーム → 共通リミッター | 独立に -20 dBFS へ正規化された2系統が同時に鳴ると理論上 +6 dB（完全相関）〜+3 dB（無相関）。部分相関を想定した統計的妥協点として -3 dB を採る |

これらの値は `AudioProcessingSettings` に集約され、コード内コメントにも同じ根拠を残しています。

### 2.5 バックプレッシャー（要件27）

`SttScheduler` の設計:

- `Enqueue` はブロックしない（pump スレッドから呼ばれるため）。
- メモリ上のキューが `MaxInMemorySeconds`（既定 120 秒 ≒ 7.7 MB）を超えたら、
  以降のチャンクは **ディスクへ退避**（`.stt-spill/`）。
- **ドロップは行わない。** 3 時間分のバックログでも約 690 MB のディスクを使うだけで、
  RAM は上限で頭打ちになります。
- 遅延は `SttStatus.LatencySeconds` として UI に
  「文字起こし処理遅延: 18秒（未処理 5 件 / 40秒）」の形で表示されます。
- 正常終了時に spill ディレクトリは削除されます（要件28）。

## 3. 音声認識

### 3.1 ストリーム別 VAD ゲーティング

要件38は「発言元は AI 推測ではなく録音元ストリームで決定する」ことを求めています。
一方でマイクと PC 音声を単純に 2 本とも常時認識すると CPU コストが 2 倍になります。

採用した方式:

- マイク用・PC音声用に **独立した VAD とチャンカー**を持たせ、
  発話が検出されたストリームのみをチャンク化して認識キューへ投入する。
- 会議では通常どちらか一方しか発話していないため、**推論負荷は実質 1 ストリーム分**。
- チャンクは生成時に発生元ストリームが刻印されるため、発言元は常に「録音の事実」。

### 3.2 VAD の方針（要件36）

小さな声・相槌・語尾を削らないことを最優先にしています。

- しきい値は固定値ではなく **推定ノイズフロア + 8 dB**（静かな部屋ではしきい値も下がる）。
- 発話開始判定は **40 ms**（日本語の「はい」は 150〜250 ms なので十分捕捉）。
- **600 ms のハングオーバー**で語尾・母音の減衰を保持。
- チャンクには **300 ms のプリロール**を必ず前置し、語頭の子音を欠かない。

### 3.3 whisper.cpp の設定

| 設定 | 値 | 理由 |
| --- | --- | --- |
| `WithNoContext()` | 有効 | 1つのエンジンにマイク／PC音声のチャンクが交互に入るため、デコーダの文脈を持ち越すと「部屋の発言に条件付けされた、流暢だが誤った remote 側の文」が生成される。会議記録では最悪の故障モード |
| サンプリング | 既定は greedy（beam 1） | ビームサーチは約2倍のコスト。会議音声では差が小さく、余裕のある機体でのみプロファイルが beam を上げる |
| `NoSpeechProbability > 0.85` を破棄 | 有効 | Whisper は無音に対し「ご視聴ありがとうございました」等の定型句を出すことがある。文字列のブラックリストではなく **モデル自身が出す指標** で落とすため、正規の発話を誤削除しにくい |
| 最短入力 1 秒 | 無音パディング | whisper.cpp が 1 秒未満を扱えないため。短い返事を捨てずに認識させる |

### 3.4 性能自動調整（要件33-35）

ユーザーは「高速／標準／高精度」を選びません。

1. `CapabilityProbe` が **実測**します（CPU 型番は使いません）。
   96×96 の密行列積を 1 スレッド／推奨スレッド数で実行し、
   ウォームアップ後のスループットを i5-1335U の P コア相当 = 1.0 として正規化。
   同じ型番でも省電力設定・熱・充電状態で 2 倍以上変わるため、型番判定では不十分です。
2. `ProfileSelector` が推定 RTF（= 推論時間 / 音声長）が **0.6 以下** に収まる中で
   最良のモデルを選びます。0.6 は、密な発話区間が平均より遅いことを見込んだ余裕です。
3. RAM が「モデル所要量 × 3」に満たない場合は選びません（Windows・ブラウザ・
   会議クライアントと共存させるため）。
4. 実行中の実測 RTF が 0.95 を超え続けた場合、要件70の順で機能を落とします。

```
話者分離 OFF → STT を軽量モデルへ → ローカルLLM OFF
（録音・保存・文字起こし自体は最後まで維持）
```

### 3.5 GPU（要件35）

**GPU は必須にしていません。CPU が唯一の必須経路です。**
Whisper.net は OpenVINO エンコーダを指定できますが、
Intel 内蔵GPU での安定性・ドライバ依存・配布サイズ増を勘案し、
既定では有効化していません。将来的に有効化する場合も CPU フォールバックは維持します。

## 4. 話者分離（実験的・要件39-41）

- 各発話区間から **MFCC 1〜12 の平均と標準偏差（24次元）** を作り、L2 正規化。
- 既存クラスタとのコサイン類似度が **0.82** 以上なら同一話者、なければ新規クラスタ。
- クラスタはキャプチャストリームごとに独立（マイク側と PC 音声側で番号を共有しない）。
- クラスタ上限 8。

**限界を明記します。** これはニューラル話者埋め込みではありません。
重なった発話は分離できず、声質の似た2人は統合され、
マイクとの距離が変わった同一人物は分割されることがあります。
そのため:

- 発言元の「マイク / PC音声」は **常に**録音元ストリームで決定され、話者分離の成否に依存しません。
- 人物名を AI が推測することはありません。`Speaker 1`, `Speaker 2` のみを付与し、
  実名はユーザーが入力した場合のみ表示されます（会議内の同一話者へ一括反映）。
- 性能不足時は最初に切り捨てられます。

## 5. 議事録生成（実験的・要件44-47）

2つの生成器があります。

| 生成器 | 依存 | 動作 |
| --- | --- | --- |
| `ExtractiveMinutesGenerator` | なし（常に利用可能） | 決定・アクション・継続検討のキューフレーズに一致する文を **原文のまま**タイムスタンプ付きで抽出。10分ブロックごとに議題を整理 |
| `LocalLlmMinutesGenerator` | llama.cpp + GGUF | ブロック要約（map）→ 4 セクション生成（reduce）の 2 段構成。失敗時は抽出型へフォールバック |

共通の方針:

- **録音停止後にユーザーがボタンを押した場合のみ実行**（リアルタイム生成なし）。
- 出力の骨格は `MinutesTemplate` が組み立てるため、モデルが脱線しても6セクションは必ず存在します。
- プロンプトは「文字起こしにない情報を書かない」「担当者・期限が明記されていなければ
  必ず `要確認`」「人物名を推測しない」を明示。
- 進捗は実際に処理したブロック数（偽の進捗バーではありません）。

## 6. 永続化とクラッシュ復旧（要件50-51）

```
2026-09-07_1430_Meeting/
├── meeting.wav            逐次書き込み（ヘッダを毎フラッシュで更新）
├── transcript.txt / .md   停止時・編集時に生成
├── minutes.txt / .md      「議事録を生成」実行時
├── metadata.json          原子的書き込み（.tmp → Replace）
├── session.journal        録音中のみ存在。追記専用 JSON Lines
└── .stt-spill/            バックログ退避用。正常終了時に削除
```

- **WAV ヘッダ自己修復**: フラッシュのたびに RIFF/data サイズを実書き込み量で書き直します。
  プロセスが強制終了しても、残ったファイルはそのまま再生できます（修復ツール不要）。
- **追記専用ジャーナル**: 認識結果・編集・進捗を1行1JSONで追記。
  電源断で最終行が途中で切れても、その行を読み飛ばすだけで直前までが完全に復元されます
  （テスト `JournalReplayReconstructsEverySegmentEvenAfterATornLastLine`）。
- **起動時スキャン**: 保存先に「完了していないジャーナル」を持つフォルダがあれば
  復旧ダイアログを表示します。「復旧しない」を選んでも音声ファイルは削除しません。

## 7. デバイス変更とスリープ（要件52-53）

- キャプチャが予期せず停止した場合、最大 5 回・線形バックオフ（0.5s, 1.0s, ...）で
  デバイスを再解決して再接続します。成功／失敗のいずれも `CaptureFault` として
  UI に日本語で通知します。**自動復帰できない場合は明示します**（要件52）。
- スリープ抑制は `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` を
  **専用スレッド**から呼びます。スレッドプールから呼ぶとスレッド回収時に要求が失われます。
  `ES_DISPLAY_REQUIRED` は要求しません（画面ロックポリシーを上書きしない）。
  プロセス終了時に自動解除されるため、クラッシュしても設定は残りません。管理者権限は不要です。

## 8. セキュリティとプライバシー

| 項目 | 実装 |
| --- | --- |
| 会議データの外部送信 | 実装上存在しません。HTTP クライアントは `ModelDownloader` の1箇所のみ |
| クラウド STT / LLM API | 依存関係に含まれません（`Whisper.net` と `LLamaSharp` はいずれもローカル推論） |
| 許可される通信 | AIモデルのダウンロードのみ。URL は `ModelCatalog` のハードコード許可リストに限定され、HTTPS 以外は拒否。任意 URL 入力欄は存在しません |
| 整合性 | SHA-256 を必ず計算。カタログにピン留めハッシュがあれば照合し、不一致ならファイルを削除して失敗。ピン留めが無い場合は「照合できなかった」ことを明示し、計算値をローカル `models.json` に記録（以後の改竄検出に使用） |
| テレメトリー | Analytics / Application Insights / Sentry いずれも不使用。クラッシュログの自動送信なし |
| ログ | ローカルのみ。会議本文や文字起こし全文はログに複製しません（イベント・件数・処理時間のみ） |
| 権限 | `app.manifest` は `asInvoker` |

## 9. 配布とビルド

- `dotnet publish -r win-x64 --self-contained true` による自己完結型配布。
  .NET / VC++ / Python / Node.js の事前インストールは不要です。
- **トリミングは無効**: WPF はトリム非対応であり、Whisper.net と LLamaSharp は
  ネイティブアセットと型をリフレクションで解決します。ZIP がやや大きくなる代わりに
  「展開したら動く」ことを優先しました。
- **単一 EXE にはしていません**: 要件でも必須とされておらず、
  単一ファイル化はネイティブライブラリの展開を伴い起動が遅くなるためです。
- **llama.cpp の命令セット別レイアウトを保持しています**: LLamaSharp は
  `noavx / avx / avx2 / avx512` の 4 種のネイティブバイナリを同梱し、
  実行時に上から順にロードを試みます。RID 指定の publish は既定で
  `runtimes/<rid>/native/` を出力ルートへ平坦化するため、
  4 種が同名で衝突して `NETSDK1152` になります。
  仮に平坦化に成功しても危険です — 1 種類しか同梱されず、
  AVX-512 非対応の PC で AVX-512 ビルドを読み込むと
  「不正な命令」で即座に落ちます。そのため publish ターゲットで
  元のパッケージ内パスへ戻し、CI で 4 種の存在とルートに
  `llama.dll` が無いことを検証しています。
- CI は `windows-latest` 上で restore → build → test → publish → ZIP → artifact を実行し、
  publish 出力に `MeetingRecorder.exe` / ランタイム / whisper ネイティブが存在すること、
  および **AIモデルが混入していないこと** を検証します。

## 10. CI で検証できないこと

`docs/WINDOWS_E2E_TEST.md` と `TEST_RESULTS.md` に一覧があります。要点のみ:

GitHub-hosted の Windows ランナーには実マイク・実スピーカー・実オーディオセッションが
ありません。したがって **CI のビルド成功は WASAPI 実機動作の確認を意味しません。**
実機確認が必要な項目（マイク録音、ループバック取得、Zoom/Meet/Teams 実音声、
長時間録音、CPU/RAM 実測、SmartScreen、i5-1335U での STT 実性能）は
すべて「Windows 実機確認が必要」として分類しています。
