# Meeting-Capture 実機テスト手順書（日本語精度 / 録音品質 / 1時間安定性）

**このドキュメントの位置づけ**

[`docs/WINDOWS_E2E_TEST.md`](WINDOWS_E2E_TEST.md) は「機能が動くか」を 47 項目で確認する手順書です。
本書はそのうえで、**品質を数値で測る**ための手順書です。対象は次の 3 点に絞ります。

1. 日本語文字起こし精度
2. 録音品質
3. 1時間連続利用時の安定性

結果は [`TEST_RESULTS.md`](../TEST_RESULTS.md) に記録します。

**優先順位（本書のすべての判断はこれに従います）**

> **文字起こしよりも録音の確実性を優先する。**

文字起こしは同じ音声から何度でもやり直せます。録音の欠落・破損はやり直せません。
したがって録音の失敗は重大不具合として扱い、**文字起こし精度がどれほど高くても、
録音に問題があればリリースしません。**

**本書で使う付属ツール**（Python 3.11 以上。テストPCではなく解析用PCで実行して構いません）

| ツール | 用途 | 章 |
| --- | --- | --- |
| [`tools/cer.py`](../tools/cer.py) | CER（文字誤り率）の計算 | 8 |
| [`tools/wav_quality.py`](../tools/wav_quality.py) | WAV のクリップ・欠落・レベル・分ごとの推移 | 15, 25 |
| `MeetingRecorder.exe --diagnose` | デバイス・ループバック・モデルの自己診断 | 3 |

いずれも導入前に自己診断を通してください（それぞれ `selftest` サブコマンドがあります）。

```
python3 tools/cer.py selftest
python3 tools/wav_quality.py selftest
```

| ID | 音声 | 推奨時間 | 目的 |

## 5. 正解文字起こしの作成

CER を計算するには、人間が確認した**正解文**が必要です。

* 言い間違い、言い淀み、同じ言葉の繰り返しも、**実際の発話どおり**記載します。
* **AI が作った文字起こしをそのまま正解データにしてはいけません。**
  最終的に人間が音声を聞いて確認します（AI 出力を下書きにすること自体は構いませんが、
  下書きを使った場合はその旨を記録してください。誤りが正解側に残ると、以後の比較がすべて狂います）。
* 文字コードは **UTF-8**、拡張子は `.txt` とします（`tools/cer.py` は UTF-8 前提です）。
* ファイル名の推奨: `J01.ref.txt`（正解） / `J01.small.txt`（認識結果）。

句読点・改行・全角半角は CER 計算前に正規化されるため（8 章）、正解文の書式を厳密に揃える必要はありません。
**揃える必要があるのは「何と言ったか」だけ**です。

## 6. 日本語文字起こし精度テスト

### 6.1 比較するモデル

同一音声を最低限、**small / medium / large-v3-turbo** の 3 モデルで文字起こしします。

### 6.2 同じ入力を 3 回使うための手順（重要）

条件を揃えるため、**同じ録音ファイル**を各モデルへ入力します。モデルごとに録音をやり直してはいけません。
本アプリでこれを担保する方法は 2 通りあります。

**方法 A（推奨）: インポート機能を使う**

J01〜J05 の音声ファイルを「音声ファイルをインポート」で読み込みます。
インポートでは元ファイルから `recognition-import.wav`（16 kHz / モノラル）を毎回作り直すため、
**3 モデルすべてがビット単位で同一の入力**を見ます。作業音声を削除する設定でも、
元ファイルが同じ場所にある限り再実行できます。

制約: インポート音声では話者推定を行いません（マイク／PC音声の区別も付きません）。
精度測定にはこれで十分です。話者分離の評価は別途 `WINDOWS_E2E_TEST.md` 側で行います。

**方法 B: アプリで録音した会議を再文字起こしする**

設定の「**文字起こしが完了したら作業用音声を削除する**」を**オフ**にしてから録音してください。
オンのままだと、1 回目の文字起こしが完了した時点で `recognition-mic.wav` /
`recognition-system.wav` が削除され、**2 つ目のモデルで測定できなくなります**。

> 作業音声を消してしまった録音は、`meeting.wav` をインポートすれば文字起こしできますが、
> その場合マイク／PC音声の区別は失われ、方法 A と同じ条件になります。

### 6.3 1 モデル分の実行手順

1. 設定画面でモデルを選択する（未取得ならダウンロードし、SHA-256 の照合結果を確認する）。
2. アプリを再起動する（モデル読み込み時間とピーク RAM を毎回同じ条件で測るため）。
3. 監視スクリプト（21 章）を開始する。
4. 音声を読み込み、文字起こしを開始する。**開始時刻を秒まで記録する。**
5. 完了したら終了時刻を記録し、`transcript.txt` を `J01.small.txt` のような名前で保存する。
6. 監視スクリプトを停止し、ピーク RAM と CPU を記録する。
7. ログから該当区間を切り出して保存する。

## 7. 測定項目

モデルごとに以下を記録します。「取得元」は、その数値をどこから読むかです。

| 項目 | 内容 | 取得元 |
| --- | --- | --- |
| 音声時間 | 入力音声の時間 | `python3 tools/wav_quality.py analyze <wav>` の「長さ」、または `metadata.json` の `durationSeconds` |
| 処理時間 | 文字起こし開始〜完了 | ストップウォッチ＋ログのタイムスタンプ |
| CER | Character Error Rate | `tools/cer.py`（8 章） |
| 明確な脱落 | 発言そのものが抜けた箇所 | 正解文との突き合わせ（人間） |
| 幻覚 | 実際には発言していない文章 | 同上。特に無音区間の直後 |
| 固有名詞誤り | 人名・会社名・専門用語 | 4 章で作った固有名詞リストと突き合わせ |
| タイムスタンプ | 発話位置とのズレ | `transcript.md` の時刻と実音声の突き合わせ（抜き取り 5 箇所） |
| 最大RAM | 文字起こし中の最大使用量 | 21 章の監視スクリプト（ピークワーキングセット） |
| CPU | 処理中のおおよその使用率 | 同上 |
| エラー | 停止・クラッシュ等 | ログ、画面表示 |

**幻覚の数え方**: 「正解に存在しない連続した文」を 1 件とします。1 文字単位の誤りは CER 側で数えるため、
ここでは二重に数えません。定型句（「ご視聴ありがとうございました」等）が出た場合は、
その発生時刻と直前の音声の状態（無音・雑音・BGM）も記録してください。

## 8. 日本語精度の主指標: CER

日本語は単語境界が明確でないため、WER ではなく **CER（文字誤り率）**を主指標とします。

```text
CER = (置換文字数 + 削除文字数 + 挿入文字数) ÷ 正解文字数
```

例:

```text
正解: 本日の会議を開始します
認識: 本日の会議を開示します
```

正解 11 文字に対し置換 1 文字なので、CER = 1 ÷ 11 = **9.09 %** です。

### 8.1 比較前の正規化

CER 計算前に、以下**だけ**を統一します。

* Unicode NFKC（半角／全角の統一を含む）
* 空白（半角・全角・タブ・改行）の除去
* 句読点・記号の除去

以下は**勝手に正解扱いしません**。すべて誤りとして数えます。

* 漢字とひらがなの違い（「会議」と「かいぎ」）
* 人名誤変換
* 数字表記（「10時」と「十時」）
* 固有名詞誤り

表記揺れは、**数値を甘くするのではなく別途注記**します。`tools/cer.py` は
「よく置き換わった文字」を頻度順に出力するので、注記はそこから書けます。

### 8.2 計算の実行

```
python3 tools/cer.py score --ref J01.ref.txt --hyp J01.small.txt
python3 tools/cer.py batch pairs.tsv          # 1行 = ID<TAB>正解ファイル<TAB>認識ファイル
python3 tools/cer.py normalize --in J01.ref.txt   # 実際に比較される文字列を確認する
```

`batch` は 29 章の表に貼れる Markdown を出力します。合計行は文字数で重み付けした値であり、
各行の CER の単純平均ではありません（短い音声の誤りが過大評価されるのを避けるためです）。

実装上の注意:

* 編集距離は厳密計算です。長い文章では対角帯を広げながら解くため、
  1 時間分（約 17,000 文字・CER 8 % 程度）で 1 分弱かかります。`--exact` は全行列版で、
  帯計算の検算用です（短い文章で使ってください）。
* CER は 100 % を超えることがあります。実装の異常ではなく、幻覚によって
  正解より長い文章が出力された場合に起こります。

## 9. 文字起こし精度の暫定評価基準

以下は**推奨の暫定基準であり、実績値ではありません。** 実測後、基準そのものを見直してください。

**J01: 明瞭な1名音声**

| CER | 評価 |
| ---: | --- |
| 0〜10 % | 良好 |
| 10〜15 % | 実用候補 |
| 15〜25 % | 要改善 |
| 25 % 以上 | 問題あり |

**J02: 通常会議**

| CER | 評価 |
| ---: | --- |
| 0〜15 % | 良好 |
| 15〜20 % | 実用候補 |
| 20〜30 % | 要改善 |
| 30 % 以上 | 問題あり |

J03〜J05 は難条件のため、CER だけで合否を決めません。次を別途確認します。

* 発言全体の脱落
* 無関係な文章の生成（幻覚）
* 人名の継続的誤認識（1 回の誤変換より、同じ人名を最後まで間違え続けることのほうが実害が大きい）

## 10. Whisper Context A/B テスト

### 10.1 比較したい 2 条件

| 条件 | 内容 |
| --- | --- |
| A | `NoContext = ON`（現在の実装。窓ごとに文脈を捨てる） |
| B | 同一音源内では文脈を維持し、音源切替時のみリセットする |

同じ J02・J04 音源を使い、CER / 固有名詞認識 / 前後文脈を必要とする発言 / 幻覚 / 処理時間を比較します。

判断: 条件 B で CER が下がり、かつ幻覚が増えないなら、**音源単位 Context 方式を採用候補**とします。
数値差が小さい場合は、実装を複雑化せず現方式を維持します。

### 10.2 現状: 条件 B は現行ビルドでは実行できません

理由は依存ライブラリの制約です。**アプリ側の設定では切り替えられません。**

1. 現在の実装は
   [`WhisperSpeechRecognizer.cs`](../src/MeetingRecorder.Stt/WhisperSpeechRecognizer.cs) で
   `.WithNoContext()` を呼んでいます。
2. Whisper.net 1.8.1 の `WhisperProcessorBuilder.WithNoContext()` は
   `NoContext = true` を設定するだけで、**false を設定する API がありません**
   （[WhisperProcessorBuilder.cs L103-L107](https://github.com/sandrohanea/whisper.net/blob/1.8.1/Whisper.net/WhisperProcessorBuilder.cs#L103)）。
   `WhisperProcessorOptions.NoContext` は `bool?` で、未設定なら whisper.cpp の既定に従います。
3. whisper.cpp の `whisper_full_default_params` は `no_context = true` が既定で、
   `whisper_full` の呼び出しごとに `prompt_past` を空にします。

したがって「`.WithNoContext()` を消す」だけでは条件 B にはなりません（既定が同じ挙動のため、
**何も変わらないのに変わったつもりになる**のが最悪の形です）。条件 B を実測するには、
次のいずれかの実装変更が先に必要です。

| 方式 | 内容 | 備考 |
| --- | --- | --- |
| a | `NoContext = false` を設定できるよう Whisper.net を更新／パッチする | 上流に API 追加が必要 |
| b | 直前の窓の認識結果末尾を次の窓のプロンプトとして渡し、音源切替でリセットする | 窓ごとにプロセッサを作り直すため処理時間が増える。増分は条件 B の不利側に出る |
| c | `whisper_full_params` を独自 P/Invoke で構築する | 依存追加は不要だが、ネイティブ構造体のレイアウトに追随する保守コストが発生する |

**本テストでは 10 章を「実施不可（依存制約）」として記録し、上記のいずれかを実装したビルドで再度実施してください。**
実装する場合、条件 B は既定にせず、テスト用の明示的な切り替えとして入れることを推奨します。
文脈の持ち越しは、マイクと PC 音声という別系統の発話が 1 つのエンジンを共有する本アプリでは、
「流暢だが誤った文」を生む既知のリスクがあります（[`ARCHITECTURE.md` 3.6](ARCHITECTURE.md#36-whispercpp-の設定) 参照）。

### 10.3 あわせて確認したい既知の懸念（プロンプトの文字化け）

Whisper.net 1.8.1 は初期プロンプトを `Marshal.StringToHGlobalAnsi` でネイティブへ渡します
（[WhisperProcessor.cs L474-L481](https://github.com/sandrohanea/whisper.net/blob/1.8.1/Whisper.net/WhisperProcessor.cs#L474)）。
Windows における .NET の ANSI マーシャリングはシステム ANSI コードページ（CP_ACP）を使うため、
UTF-8 を前提とする whisper.cpp に対し、**日本語プロンプト
「以下は会議の日本語の音声です。句読点を付けて書き起こします。」が化けて渡っている可能性**があります
（コードページが 65001 でない環境の場合）。

このプロンプトは「日本語に句読点を付けさせる」ために入れているものです。効いていなければ、
出力は句読点の少ない、読みづらい文になります。次の手順で確認してください。

```powershell
# システム ANSI コードページ（932 なら Shift_JIS、65001 なら UTF-8）
[System.Text.Encoding]::Default            # Windows PowerShell 5.1 で確認する
(Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Nls\CodePage').ACP
```

| 確認 | 記録 |
| --- | --- |
| ACP の値 |  |
| `transcript.txt` に句読点があるか（J01 の 100 文字あたりの句読点数） |  |
| ログに Whisper 由来の警告があるか |  |

句読点がほとんど出ない場合、**モデルの精度ではなくプロンプトの受け渡しが原因**の可能性があります。
その場合は不具合として記録してください（32 章の書式）。CER 自体は句読点を除去して計算するため
この問題の影響を受けませんが、読みやすさと文の切れ目には影響します。

## 11. Whisper モデル選定

各モデルについて、精度 / 処理時間 / RAM / 安定性を比較します。

特に重要なのは、**large-v3-turbo が本当に日本語で最良なのかを実測すること**です。
モデル名やサイズだけで「最高精度」と判断しません。

参考値（実測の予想ではなく、比較の出発点）:

| モデル | カタログの相対コスト | CI ランナーでのピークワーキングセット |
| --- | ---: | ---: |
| small | 1.0 | （未測定） |
| medium | 3.6 | 1,364 MB |
| large-v3-turbo | 7.4 | 1,085 MB |

相対コストはエンコーダーの計算量から出した推定値で、デコーダーが 4 層しかない
large-v3-turbo には悲観的です（CI ランナーでの turbo / medium 実測比は 1.72、推定比は 2.06）。
**基準PCでの実測が本テストの目的**なので、この表の値と一致しなくても異常ではありません。
乖離した場合はその事実を記録してください。

## 12. RTF の計算

```text
RTF = 処理時間 ÷ 音声時間
```

60 分の音声を 30 分で処理した場合、RTF = 30 ÷ 60 = 0.5 です。小さいほど高速です。

| RTF | 60分音声の処理時間 |
| ---: | --- |
| 0.25 | 約 15 分 |
| 0.5 | 約 30 分 |
| 1.0 | 約 60 分 |
| 2.0 | 約 120 分 |

これは評価値であり、合否基準ではありません。ただし設定画面が表示する推定処理時間と
実測 RTF が大きく食い違う場合は、推定式の見直し対象として記録してください。

## 13. 録音品質テスト

文字起こし精度とは分離して評価します。**録音品質試験では Whisper を動かしません**
（本アプリは停止後に自動で文字起こしを始めないため、単に実行しなければ達成されます）。

| ID | Mic | PC音声 |
| --- | --- | --- |
| A01 | ○ | × |
| A02 | × | ○ |
| A03 | ○ | ○ |
| A04 | ○ | ○（Zoom 等を使用） |

A01 / A02 はレベルメーター下のチェックボックス（ミュート）で一方だけを録音します。
ミュートした系統はブロック生成後にゼロで埋められるため、**作業音声ファイルは作られ、
中身は厳密な無音になります**。ファイルが存在すること、その系統の音が本当に入っていないこと、
そして**残した側の音が欠けていない**ことを確認してください。
（`wav_quality.py` はミュートした側のファイル全体を「ゼロ連続」として報告します。
A01 / A02 ではそれが正常です。）

各条件で必ず記録すること: 開始時刻、停止時刻、ストップウォッチによる実測長、
画面下部の診断表示（`バッファ溢れ` / `無音補間` / `同期補正`）の最終値。

## 14. 発話テスト内容

各条件で以下を発声します。

```text
あいうえお
かきくけこ
さしすせそ
たちつてと

本日は Meeting-Capture の録音品質を確認しています。

これは少し大きい声です。
```

特に **カ行・サ行・タ行・パ行**の発話開始（語頭の子音）を確認します。
目的は、旧 Noise Gate で懸念していた**子音欠落が発生していないか**の確認です。
現在の実装にはゲート／AGC／コンプレッサー／リミッターがありません
（型そのものが存在しないことを自動テストが毎ビルド検査しています）。
本章はその設計が実機でも成立していることの確認です。

「これは小さい声です／通常の声です／少し大きい声です」は 16 章で使うので、
**同じマイク距離のまま、声量だけを変えて**発声してください。

## 15. 録音品質チェック

録音後、`tools/wav_quality.py` で機械的に測り、そのうえで Audacity 等の波形表示ソフトで確認します。

```
python3 tools/wav_quality.py analyze meeting.wav --expect-seconds 305.2
python3 tools/wav_quality.py analyze recognition-mic.wav recognition-system.wav --markdown
```

MP3 で保存した場合は、比較の基準にしないでください（非可逆圧縮後の波形です）。
録音品質の測定は WAV に対して行います。設定で WAV を選ぶか、`recognition-*.wav` を対象にします。

### 15.1 音声欠落

発話した内容が途中で消えていないこと。

`wav_quality.py` の「ゼロ連続」は、**厳密に振幅 0 が連続した区間**です。本アプリは
ノイズゲートを持たないため、実マイクの録音に長いゼロ連続が現れることは通常ありません。
検出された場合は、その時刻を再生して実際に音が消えているかを確認します。

例外: PC 音声（`recognition-system.wav`）は、**何も再生していない間 WASAPI ループバックが
何も返さない**ため、その区間はゼロで埋められます。これは正常です。画面の `無音補間` の値が
増えるのも同じ理由です。**PC 音声を再生していた区間のゼロ連続だけが異常**です。

**合格基準: 欠落 0 回**

### 15.2 発話開始

「か」「さ」「た」「ぱ」等の語頭が消えていないこと。波形の立ち上がりが切れていないかを目視し、
聴感でも確認します。

**合格基準: 明確な語頭欠落 0 回**

### 15.3 クリッピング

波形が最大振幅へ張り付いていないこと。`wav_quality.py` の「クリップ候補」は、
32,700 以上の振幅が 3 サンプル以上続いた箇所です。検出された箇所は、次の 2 つを区別します。

| 種別 | 判定方法 | 扱い |
| --- | --- | --- |
| 入力時点でクリップ | Windows の入力レベルが過大。`metadata.json` の `sourceClipped` が `true` | アプリでは修復できない。設定の見直しで対応 |
| アプリの Gain 処理によるクリップ | 入力が過大でないのに出力が張り付いている | **アプリ側不具合。0 件を必須とする** |

`metadata.json` の `appliedGainDb` と `sourceClipped` を必ず記録してください。
アプリは目標ピークを超えないようゲインを決め、ハードクリップしない設計になっています。
**後者が 1 件でもあれば録音機能として不合格**です。

## 16. 固定 Gain の確認

同一ファイル内で、小さい声 / 通常音量 / 大きい声の**相対的な音量差が維持されている**ことを確認します。

手順:

1. Audacity で 3 つの発話区間を選択し、それぞれのピーク（または RMS）を読む。
2. 元音声（別途スマートフォン等で同時録音したもの、または入力レベルメーターの記録）と比率を比べる。
3. 元音声で「大声 = 小声の約 4 倍」なら、処理後も概ね同じ比率であること。

次の場合は NG です。

* 小声だけが急激に大きくなる
* 大声だけが圧縮される
* 無音部分が持ち上がる（ノイズフロアが上下する）

これは AGC / Compressor に近い動作が残っている可能性を示します。
本アプリのゲインは録音全体で一定の係数であり、`wav_quality.py --per-minute` の
RMS 推移が発話内容と無関係に平坦化していく場合も、同じ疑いとして記録してください。

## 17. マイク / PC音声分離

`recognition-mic.wav` と `recognition-system.wav` を個別に再生します。

| 側 | 確認 |
| --- | --- |
| Mic 側 | PC 内部音声だけが大量に混入していないこと |
| System 側 | マイク音声だけが大量に混入していないこと |

スピーカー再生でテストすると、**PC 音声がスピーカーから出てマイクに回り込むのは物理現象**であり、
アプリの不具合ではありません。分離の評価はヘッドセット使用時に行い、
スピーカー使用時の回り込み量は「参考値」として別に記録してください。
物理的に分離できない構成の場合は、その理由（スピーカー再生・ハンズフリー HFP など）を記録します。

## 21. 1時間中の監視

10 分ごとに記録します。アプリ画面下部の診断表示（CPU / RAM / 書き込み / バッファ溢れ /
無音補間 / 同期補正）が一次情報です。タスクマネージャーは全体 RAM と Disk の確認に使います。

| 時刻 | CPU | Meeting-Capture RAM | 全体RAM | Disk | バッファ溢れ | 無音補間 | 同期補正 | UI |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 0分 |  |  |  |  |  |  |  |  |
| 10分 |  |  |  |  |  |  |  |  |
| 20分 |  |  |  |  |  |  |  |  |
| 30分 |  |  |  |  |  |  |  |  |
| 40分 |  |  |  |  |  |  |  |  |
| 50分 |  |  |  |  |  |  |  |  |
| 60分 |  |  |  |  |  |  |  |  |

UI 欄: `正常` / `少し遅い` / `操作困難` / `フリーズ`

**バッファ溢れ（BufferOverruns）は 0 のままであるべき値です。** 1 以上になった時点で、
その瞬間に音声が捨てられています。時刻とともに必ず記録してください。

**無音補間**は PC 音声を再生していない間も増えます（15.1 参照）。増加そのものは異常ではなく、
**音が出ていたはずの区間で増えている**ことが異常です。

自動記録したい場合（10 秒間隔で CSV に追記します。ASCII のみで書いてあるので、
Windows PowerShell 5.1 でもそのまま貼り付けられます）:

```powershell
$out = "$env:USERPROFILE\Desktop\mc-monitor.csv"
"time,cpu_percent,working_set_mb,private_mb,handles,threads" | Out-File $out -Encoding ascii
$last = $null
while ($true) {
  $p = Get-Process MeetingRecorder -ErrorAction SilentlyContinue
  if ($p) {
    $now = Get-Date
    $cpu = if ($last) { [math]::Round((($p.TotalProcessorTime - $last.cpu).TotalSeconds / ($now - $last.at).TotalSeconds) * 100 / [Environment]::ProcessorCount, 1) } else { 0 }
    "{0:HH:mm:ss},{1},{2},{3},{4},{5}" -f $now, $cpu, [math]::Round($p.WorkingSet64/1MB), [math]::Round($p.PrivateMemorySize64/1MB), $p.HandleCount, $p.Threads.Count | Out-File $out -Append -Encoding ascii
    $last = [pscustomobject]@{ at = $now; cpu = $p.TotalProcessorTime }
  }
  Start-Sleep -Seconds 10
}
```

同じスクリプトを 27 章の文字起こし計測にも使います（そちらではピーク値が本命です）。

## 22. メモリリーク確認

RAM 使用量が時間とともに**一方向に増え続けていないか**を確認します。次のような形はリークを疑います。

```text
開始   200 MB
10分   240 MB
20分   280 MB
30分   450 MB
40分   700 MB
50分 1,200 MB
60分 2,000 MB
```

多少の上下は正常です。**開始時と終了時の差だけでリークと断定しません。**
判断材料は次の 3 つです。

* 単調増加であること（下がる局面がない）
* 増加が録音の経過時間に比例していること
* ハンドル数・スレッド数も増え続けていること（上の CSV に含めています）

疑わしい場合は、停止後 5 分間放置して RAM が戻るかどうかも記録してください。

## 24. 録音時間の一致

ストップウォッチによる実測時間とファイルの時間を比較します。

```
python3 tools/wav_quality.py analyze meeting.wav --expect-seconds 3603
```

```text
実測録音時間: 60:03
ファイル時間: 60:03
```

数秒以上の差がある場合は要調査です。特に次は重大です。

```text
実録音 60分 → 保存 59分20秒
```

`同期補正`（DriftCorrectedMs）はマイクと PC 音声のクロック差を吸収するために意図的に
捨てたサンプル量です。この値と不足分が対応しているかを確認してください。対応していれば設計どおり、
対応していなければ未知の欠落です。

「文字起こしがおかしい」だけでは記録として成立しません。次の形式で残します。

```text
Test ID:
日時:
Git commit:
PC:
Meeting app:
Whisper model:

発生時刻:
再現手順:

期待結果:

実際の結果:

音声時刻:

ログ:

再現率:
例: 3回中3回
```

可能であれば、問題が発生した音声ファイルをそのまま保存してください。
`meetingrecorder.log` の該当時刻前後（前後 2 分）と、`metadata.json` も添付します。
録音に関わる不具合では、**音声ファイルそのものが唯一の一次証拠**です。上書きしないでください。

## 33. 最終判定

### A. 録音（最優先）

以下がすべて 0 件であること。

```text
録音の途中停止 / ファイル破損 / Dropout / Mic消失 / System消失 /
Gain処理由来のClip / Crash / Freeze / バッファ溢れ
```

これを満たさない場合、**文字起こし精度が高くてもリリースしません。**

### B. 文字起こし

モデルごとに CER / 処理時間 / RAM / 幻覚 / 脱落を比較し、
「最も大きいモデル」ではなく、

> **実際の日本語会議で最も精度と処理時間のバランスが良かったモデル**

を既定値とします。判断は基準PCでの実測に基づきます。CI ランナーの数値や
カタログの相対コストは参考にとどめます。

### C. 長時間安定性

60 分連続録音で、Crash なし / Freeze なし / Dropout なし / 音声ファイル破損なし を最低条件とします。

## 34. 最終レポート

テスト完了後、以下の形式で整理し、`TEST_RESULTS.md` に反映します。

1. テスト環境（PC / OS / アプリ version / commit）
2. 録音品質（結果・問題点）
3. 1時間連続録音（結果・CPU・RAM）
4. Whisper 比較（small / medium / large-v3-turbo）
5. 日本語 CER（テストデータ別）
6. Context A/B 比較（実施できたか、できない場合はその理由）
7. 発見した不具合（再現条件）
8. 推奨 Whisper モデル（実測結果を根拠として決定）
9. リリース可否（`GO` / `CONDITIONAL GO` / `NO-GO`）
10. 残課題

推定値と実測値を同じ表に混ぜないでください。混ざった時点で、
その表はどちらの根拠にも使えなくなります。

## 35. 最重要判断基準

```text
録音成功 → 音声品質 → 文字起こし成功 → 文字起こし精度
```

この順に重要度を設定します。

文字起こしモデルの変更で改善できる問題と、録音時点で失われて二度と復元できない問題を、
同じ重要度で扱わないでください。

**録音データが正しく残ることを最優先の合格条件とします。**
